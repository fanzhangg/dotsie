Data

How the spots data is made

The sources say what a place is. Code measures what can be measured. A model is asked only what takes judgment, in a form code can check, and every answer is kept with its reason, so any pick can be traced back to where it came from.

Four rules

  1. 1 Keep what the sources say Every record goes into the store as Wikidata, Wikipedia or the Park Service gave it. Nothing is filtered or judged on the way in, and records are linked only by identifiers they share, so any later judgment can be made again from the source.
  2. 2 Measure what can be measured Whether a place is inside a city or a park, how much people read about it, which records are the same place: these are facts, so code works them out, the same way every time.
  3. 3 Ask a model what rules can’t answer Is this somewhere people go? Which few are worth a special trip? How would a good guidebook put it? Which photo shows it? Each is a narrow question with a typed answer.
  4. 4 Show the working A pick comes with why, a guide with what it left out, a paragraph with its sources. Any place can be followed through every step, without asking a model again.

From sources to a guide

Two runs. The first collects, every month, and asks no model. The second writes a destination’s guide from what the first collected, when someone asks for it.

Code A model

Collect · every state, on the 3rd of each month

  1. Code

    Fetch what changed

    Every Wikidata item in the state with coordinates; every record the NPS Data API lists; each English Wikipedia article’s text, categories and 12 months of page views; each official website’s first page. Only what changed since last month is fetched again.

  2. Code

    Link, don’t merge

    Two records from different sources are linked when they share an identifier (a park code, an NPS place ID, the same website). Records that are only probably the same place, with the same name within 1 km, are linked too, but marked as such.

  3. Code

    Publish metadata, not text

    Each state’s store goes to D1 as names, identifiers and links, never text copied from other sites: Spots data searches it.

Guide · one destination at a time, run by hand

  1. Code

    1. Candidates

    Places inside the destination’s outline (its Census place or county, or its NPS boundary) that have an English Wikipedia article or an NPS page.

  2. A model

    2. Is it a sight? Haiku

    A place people go to see or experience, still there, open to visitors, and not part of a bigger place nearby. Plus its draw, 1 to 5: how far out of their way a visitor would go.

  3. Code

    3. Shortlist

    70 sights to choose from: the most read on Wikipedia, and up to 20 that hardly anyone reads about, by their draw.

  4. A model

    4. Pick Sonnet

    The whole shortlist at once, compared with each other: what a visitor with a few days shouldn’t miss, in order, with a reason for each, and what it left out and why.

  5. A model

    5. Write Sonnet

    A one-liner and two or three paragraphs per pick, from the store’s dossier only, each paragraph with its sources. Practical facts, such as hours and fees, kept apart.

  6. A model

    6. Pictures Haiku

    Looks at up to 8 photos from Wikimedia Commons and chooses a lead photo and up to two more, each after the paragraph it shows, with its author and licence.

  7. Code

    Review, then the app

    The entries go to D1, where Guide preview shows each with what it takes to review it, and the app’s Spots page shows them to everyone.

Seattle, step by step

Each step hands the next fewer places. The model is asked only about the places that could still make the shortlist: the ones nobody reads about first, then the most read, 40 at a time, until there are enough sights.

Where the model comes in

Why not rules

The first pilots, on Seattle and Washington, decided what’s a sight with rules: lists of Wikidata types to keep and to block, a page-view floor per type, Wikipedia categories for what’s demolished or closed, and a table of exceptions. Each rule fixed one place and broke another. Blocking creative works, to drop a TV series, also dropped the Gum Wall and Smith Tower. In a city, office towers are read about as much as sights. The Tacoma Narrows Bridge of 1940, which fell that year, ranked at the top with 17,486 views a month.

“Would people go there?” is a judgment, and a model can make it the way a person would: by reading what the article and the Park Service say. Each version was measured against the same checklist of places each area must have and must never have, and against Wikivoyage’s lists of sights.

A narrow question, a typed answer

Every step asks for JSON that fits a schema, so code can read the answer and check it. Judging a place, for example, returns:

{
  "evidence":  "the facts that decide the fields below",
  "is_sight":  true,
  "exists":    true,          // false if demolished, closed for good, never built
  "visitable": "yes",         // "yes", "outside" (seen only from outside) or "no"
  "part_of":   null,          // the bigger place nearby it's seen with, by name
  "draw":      4              // 1 hardly … 5 a reason to come at all
}

The evidence comes first, so the facts are written down before the verdict. Code then decides from the fields: a sight is one that is a sight, exists, can be visited and isn’t part of another place, and a part_of counts only if it names a place really on the list nearby, and not the destination itself.

Popularity is measured, not asked

The judge is never shown page views: it says what a place is, and Wikimedia’s counts say how well known it is. The pick sees views as one hint, and is told to choose by what a visitor would get from going. A place with no article isn’t shown as “0 views”, which would read as “nobody goes”, but as an NPS page with its judged draw.

Sources are data, never instructions

An entry is written from a dossier the store puts together: the Wikipedia article, the official site’s page, the NPS pages, each inside <source> tags, which the model is told are information, never instructions to it. It writes only what they say, and each paragraph lists the sources it draws on. Afterwards, code counts how many of the entry’s 8-word phrases also appear in the sources, to spot copying, and Guide preview shows that share next to each entry.

The smallest model that does the job

Many small questions go to Haiku; the few that compare many places or need good writing go to Sonnet. Each step’s model can be changed for a run, and each model’s answers are kept apart, so two can be compared side by side before choosing.

Every answer is kept

Each answer is kept in the state’s store by its step, its place, its prompt’s version and its model, with a hash of exactly what was asked: the model, the instructions and the input. Running a guide again reuses every answer whose question hasn’t changed, and asks only what has: a place whose article was edited, a step whose prompt is a new version. Going back to an earlier model costs nothing.

Runs ask in Message Batches, at half price, most back within the hour. A run stopped while a batch is out notes it in the store and picks up its answers the next time. A question a batch can’t answer is asked again on its own.

What the model never does

  • Decide where a place is. Outlines are the Census Bureau’s and the Park Service’s, and code tests each point against them.
  • Go and look things up. It reads what the store gives it, and nothing else.
  • Rank by how well known a place is. That’s Wikipedia’s page views, counted.
  • Write without sources. Every paragraph lists the pages it was adapted from, and entries are published under CC BY-SA 4.0.
  • Run on its own. A guide is written when someone runs it for the destinations they name, and is there to review before and after.

Tracing a place

Why is a place in a guide, or not? explain.py follows it through every step from the stores alone, asking no model and changing nothing: whether it’s inside the outline, whether it’s a candidate, every answer the judge gave it (each model’s and each prompt’s), whether it made the shortlist, and whether it was picked or left out, with the model’s reason.

python3 explain.py --destination great-smoky-mountains shenandoah --names "Kuwohi,Skyline Drive"

The code is pipeline/guides.py; pipeline/README.md has every step and what it costs.
